# Что в схеме действительно реализовано

Сверка кода и пользовательского пути, 20 ноября 2026. Реализовано файловое ядро переноса и учёт процесса. Получение данных из аккаунтов, смысловой отбор и настройка принимающего сервиса требуют работы модели и доступных инструментов платформы. Поэтому наличие блока на схеме не означает наличие соответствующей сетевой интеграции в программе.

Ниже «код» означает действие, которое реально выполняет Python. «Модель» означает работу агента по инструкциям, без встроенного вызова модели из этого ядра. «Зависит от платформы» означает отдельное действие через фактически доступный инструмент; его отсутствие должно оставаться незавершённым пунктом.

## Что означают доказательства

Успешный unit-тест подтверждает конкретное поведение на тестовых данных. Прогон распакованных ZIP подтверждает самостоятельность сборки в локальной среде. Эти результаты не доказывают подключение реального облака или нативную настройку агента.

Финальный автоматический прогон 0.7: 368 тестов, 365 успешных, 3 пропуска создания символических ссылок в Windows, ошибок нет. Среда — Windows, Python 3.12.14; подготовленная конфигурация GitHub CI не выдаётся за состоявшийся прогон на Linux или Python 3.10. Основание — [TESTING.md](TESTING.md) и [test-results.json](test-results.json).

Независимый проход по двум распакованным ZIP 0.7 выполнил 54 команды и 14 проверок результата; 3 ожидаемых отказа проверили обязательный общий этап и устаревшую проверку после изменения источника. Три вымышленных источника дали 7 записей общего профиля; 6 согласованных записей приняты в переносимую папку, длительность встреч осталась отложенной. После позднего источника совпадающее правило унаследовало прежнее подтверждение, почтовые решения и отсрочка сохранились; новый вопрос касался только проектного правила. Исходные утверждения по смыслу сопоставил проверяющий агент, второй проход той же модели обозначен честно — готовые вердикты демонстрации не использовались.

Частичный пакет в пустой принимающей папке дал `checked_subset_pending_not_applied`: отложенная запись не была активирована. Другой общий профиль с дополнительным прежним правилом получателя дал `required_for_combined_profile`; решения сохранились, а активный профиль был удержан до новой общей проверки. [Отчёт 0.7](skill-forward-test-v07.json) содержит хеши испытанных ZIP и прямо фиксирует отсутствие нативного сохранения памяти, установки навыков и подключения интеграций. Предыдущие испытания физических проектных ссылок и оригиналов навыков сохранены в [отчёте 0.6](skill-forward-test-v06.json).

При объединении `--current` передаёт прежний JSON, но не прежние файлы навыков. Если сохраняемый навык с проектными зависимостями отсутствует в новом комплекте файлов, импорт блокируется, а прежняя папка остаётся неизменной. Для Windows может потребоваться короткая выходная папка: поддержка произвольно длинных путей не заявляется.

Файловая проверка подтверждает соответствие байтов билету и манифесту. Цитата подтверждает наличие текста в предоставленном источнике. Поле `verified` в настройке подтверждает, что вызывающий агент записал сообщение о действии и чтении результата. Ни один из этих трёх механизмов сам по себе не доказывает полноту аккаунта, семантическую истинность записи или выполнение внешнего действия.

## Как читать результат для пользователя

Можно честно сказать: «Подготовлен и проверен переносимый пакет; получатель создал рабочую папку; такие-то настройки реально применены доступными инструментами; такие-то части ещё требуют доступа или действия». Если выполнен только файловый этап, результат заканчивается на нём. Назвать всю настройку завершённой можно только в согласованном объёме и после фактической проверки каждой требуемой части.
