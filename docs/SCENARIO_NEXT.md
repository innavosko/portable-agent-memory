# Следующая итерация: диалог и параллельная подготовка переноса

Статус на 20 ноября 2026: в версии 0.2 реализованы карта источников, отдельные задания, параллельная обработка предоставленных файлов, сохранение ответов и продолжение. Актуальный исполняемый путь описан в [JOURNEY_V02.md](JOURNEY_V02.md). Ниже остаётся более широкий проект сценария; фоновые почтовые/дисковые интеграции и общая облачная синхронизация ещё не реализованы.

Уточнение 0.3: [конечная цель](PRODUCT_GOAL.md) — настройка принимающего агента под ключ. Для доставки сначала прорабатывается [передача папки пользователем](CLOUD_DELIVERY.md), без обязательного нового сервера. Почтовое наблюдение и фоновое ожидание отложены; приведённые ниже примеры с почтой не означают их реализацию в текущей итерации.

## 1. Пользователь может начать с любого агента

В экспортёре: «Хочу забрать свои данные». В получателе: «Хочу перенести сюда память из другого агента». Оба входа ведут к одному переносу. Если карточка уже есть, агент читает её и спрашивает только недостающее.

У получателя сразу различаем три состояния: готовый пакет уже есть; есть только исходный архив; ничего ещё не подготовлено. Готовый пакет проверяется, архив сначала превращается в проверенную память, а для третьего случая получатель готовит короткое задание исходному агенту с уже выбранным составом и местом доставки. Это избавляет пользователя от повторного объяснения задачи.

Первый вопрос должен быть о результате, а не о подключении инструментов:

> Что хотите сохранить: ваши сведения и правила, важные работы или также исходную историю? Можно выбрать несколько вариантов. Если пока не знаете, я предложу состав по доступным материалам.

Агент не требует заранее знать, что такое MCP, архив экспорта или структура памяти.

## 2. Уточняем источники и текущую готовность

Для каждого выбранного сервиса выясняем, что уже есть: доступный контекст, скачанный архив, запрошенный экспорт, папка с материалами. Сначала проверяем доступные инструменты; существующие ответы и подключения не запрашиваем заново.

Если источников два, например Claude и ChatGPT, это две независимые поставки данных в рамках одного переноса. Для каждого архива нужен свой статус и ответственный. Правило «один наблюдатель» относится к одному ожидаемому архиву, а не запрещает ждать разные архивы параллельно.

## 3. Предлагаем конкретный маршрут

После проверки возможностей агент предлагает короткий план, например:

> Сейчас могу подготовить профиль и список важных работ. Архив ChatGPT ещё ожидается; его проверяет агент-получатель через подключённую почту. Готовую память передадим файлом в чат получателя. Диск для этого не нужен.

Если выбран диск, отдельно проверяется запись у отправителя и чтение у получателя. Если выбран ручной файл, почта и диск не становятся обязательными.

При отсутствии доступа агент объясняет конкретную альтернативу: подключить доступный инструмент, выбрать другую папку или загрузить файл вручную. Уже выполненные этапы сохраняются.

## 4. Пока готовится архив, работаем с доступным

Ожидание полного экспорта не должно останавливать подготовку профиля или обсуждение работ, если соответствующие сведения уже доступны.

Предлагаем разделить процесс на независимые части:

- профиль и правила: сбор → проверка → готово;
- значимые работы: кандидаты → выбор → оформление → готово;
- каждый официальный архив: запрос → ожидание → получение → разбор;
- передача результата: пакет → доставка → проверка → применение.

Важно: фоновую проверку письма обещаем только после реального создания такой задачи. В остальных случаях агент проверяет источник в активной сессии либо продолжает после возвращения пользователя.

## 5. Проверяем профиль без повторного интервью

Показываем собранные сведения тематическими блоками. Сначала — противоречия и потенциально устаревшее; затем остальное. Для блока пользователь может подтвердить все видимые записи с перечисленными исключениями.

Пример:

> Нашёл два рабочих адреса и правила для них. Первый отмечен как основной, второй встречается в старом проекте. Оба ещё используются? Правило согласования писем показываю отдельно — его актуальность не следует автоматически из актуальности адреса.

Подтверждение принадлежности почты не означает согласие подключить её. Подтверждение описания интеграции не означает действующее подключение. Проектные правила не становятся общими.

Если пользователь исправляет сведения, повторно проверяются изменённые записи и зависящие от них решения, а не весь профиль.

## 6. Помогаем выбрать важные работы

Каждый кандидат содержит краткий результат, причину предложения, источник, доступные материалы и предполагаемый способ сохранения.

Пример:

> Нашёл завершённый анализ, идею нового продукта и повторяемый процесс подготовки отчёта. Анализ предлагаю сохранить с исходным файлом, идею — как контекст проекта, процесс — как черновик навыка. Выберите нужное; можно добавить работу, которую я не нашёл.

Не объявляем список исчерпывающим, если прочитана лишь часть истории. Навык создаётся для повторяемого процесса, а не для любого содержательного разговора.

## 7. Частичная готовность не равна завершению

Если профиль уже готов, а архив ещё ожидается, пользователь выбирает: передать готовую часть сейчас либо дождаться общего результата.

При частичной передаче явно показываются включённые и ожидаемые части. Позднее формируется обновление с устойчивыми идентификаторами, сравнением и новым подтверждением только изменившегося. Недоступный источник не считается источником без данных.

Для реализации этого режима нужны общий идентификатор переноса, отдельные задания по источникам, версии пакета и отчёт о выполнении выбранного состава. Нынешняя карточка 0.1.0 описывает одну последовательность; её нельзя выдавать за уже готовый многопоточный процесс.

## 8. Получатель применяет результат по категориям

Постоянный профиль, проектные материалы, навыки и интеграции имеют самостоятельные результаты. Пример итогового сообщения:

> Профиль подготовлен и проверен. Материалы двух проектов сохранены. Один навык требует установки. Подключение рабочего календаря осталось выполнить отдельно. Архив второго сервиса ещё ожидается.

Такой результат не обозначается общим «всё перенесено». Отчёт должен позволять продолжить с оставшегося шага, в том числе в другом разговоре.

## Что проверить до реализации расширения

- Пользователь начинает с получателя, а экспорт ещё не запрошен.
- У пользователя уже есть профиль и материалы: шаг ожидания архива пропускается.
- Два разных архива ожидаются одновременно; уведомления по одному не дублируются.
- Пока архив готовится, пользователь проверяет доступный профиль.
- У отправителя есть доступ к диску, у получателя нет.
- Пользователь меняет место доставки, сохраняя сделанную работу.
- Пользователь переносит готовую часть сейчас, затем получает обновление без дублей.
- Один и тот же адрес относится к текущему аккаунту, но старые правила для него уже неактуальны.
- Навык подготовлен, но среда получателя не умеет его устанавливать.

Проверка диалога и этих развилок возможна на вымышленных данных без подключения реальных аккаунтов. Живые веб-проверки нужны отдельно для установки, инструментов, авторизации и фактического сохранения результата.
