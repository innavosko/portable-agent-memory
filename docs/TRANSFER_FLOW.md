# Как два агента согласуют почту, диск и перенос

Оба навыка могут быть установлены и запущены одновременно. Принимающего агента можно подготовить до завершения экспорта.

Уточнение 0.4: основной маршрут — [пользователь копирует готовую папку между выбранными хранилищами и сообщает получателю](CLOUD_DELIVERY.md). Файловый маршрут реализован командами `delivery-*`; прежняя карточка `transfer-*` остаётся отдельным контрактом координации исходного архива, а не реестром публикации готового пакета. Реализация почтового наблюдения и фонового ожидания отложена. Подготовка и доставка служат [настройке принимающего агента под ключ](PRODUCT_GOAL.md).

## Что выясняют на старте

1. Откуда берутся исходные данные: доступный контекст, предоставленный архив, ссылка из письма, папка на диске.
2. Что переносится: профиль, работы, навыки, оригинальные разговоры — в выбранном сочетании.
3. Куда поступит подготовленный пакет: загрузка в чат получателя или выбранное хранилище.
4. Какие подключения реально доступны каждому агенту и какие операции они поддерживают.
5. Кто один отвечает за ожидание и получение исходного архива. Это может быть любой из двух агентов.

Известные ответы переносятся в карточке; заново весь опрос не проводится. Экспортёр не обязан иметь почту, если архив получает импортёр. Диск не нужно подключать, если пользователь выбрал загрузку файла. Подключение отправителя не даёт доступ получателю.

## Что повторять полезно

| Проверка | Зачем повторяется |
| --- | --- |
| Доступ к выбранному ресурсу в каждой среде | Аккаунты, разрешения и инструменты могут отличаться |
| Проверка целостности у отправителя и получателя | Подтверждает, что получен именно подготовленный пакет |
| Сравнение с памятью получателя | Там могут быть более новые или конфликтующие правила |
| Проверка результата после применения | Файл в чате ещё не означает сохранение постоянной памяти |

Не нужно повторять запрос того же архива, полное интервью о неизменённом профиле, подключение уже проверенного сервиса или одно и то же уведомление. При изменении записи или конфликтах уточнение оправдано.

## Карточка переноса

Карточка содержит общий идентификатор, исходный канал и описание ресурса, маршрут доставки готового пакета, двух участников, ответственного за ожидание, проверенные возможности, собственные проверки доступа, версию, события и контрольные суммы.

Переходы: **ожидание → источник готов → исходный архив получен → пакет памяти подготовлен → получатель проверил пакет → результат импорта записан**. Для профиля из уже доступного контекста скачивание архива не требуется.

Пример конфигурации: `examples/transfer-config.json`. В нём все возможности выключены и выбран ручной режим. Включать их нужно только после реальной проверки среды.

```sh
python -m portable_memory transfer-create --config examples/transfer-config.json --out private/transfer-0.json
python -m portable_memory transfer-next private/transfer-0.json --actor source-web
python -m portable_memory transfer-event private/transfer-0.json --event private/event.json --revision 0 --out private/transfer-1.json
```

Событие — JSON `{ "id": "unique-event-id", "actor": "source-web", "type": "access_checked", "data": { "channel": "email", "available": false, "evidence": "В текущей сессии нет инструмента чтения почты" } }`.

Программа записывает уже подтверждённое действие. Перед `source_ready` агент действительно проверяет источник; перед `downloaded` получает файл и вычисляет хеш; перед `data_verified` получатель проверяет пакет. Полный контракт событий и примеры последовательностей находятся в `portable_memory/transfers.py` и `tests/test_transfers.py`.

Скачивание исходного архива выполняет текущий ответственный. При необходимости он явно передаёт роль другому агенту через `handoff`. Доставка и проверка готового пакета получателем — отдельный этап. `package_ready` не означает, что файл уже загружен на Google Drive.

## Ограничения автоматизации

Карточка сама не подключает почту, не читает письма, не скачивает архив и не запускает фоновую задачу. Эти операции выполняются реальными инструментами среды. Для фонового ожидания нужны одновременно механизм исполнения и канал уведомлений. Без них предусмотрена проверка в активном сеансе или ручное возвращение пользователя.

В первой версии фиксируется одно уведомление о готовности источника. Уведомления о каждом этапе и о завершении пока не реализованы как отдельный механизм. Итоговый ответ в текущем разговоре может сообщить результат без обещания фоновой отправки.

Раздельные копии карточки в двух SaaS не синхронизируются сами. Проверка версии обнаруживает повтор или устаревшее обновление в одной истории, но не заменяет общий сервер. Для одновременных автоматических обновлений нужен единый сервис с условной записью. Пока его нет, используется один ответственный и явная передача последней карточки с остановкой предыдущего ожидания. Google Drive с двумя независимо перезаписываемыми JSON не обеспечивает такую гарантию автоматически.

Постоянная синхронизация памяти и общий сервер координации — следующие отдельные функции, не скрытые возможности текущей версии.
