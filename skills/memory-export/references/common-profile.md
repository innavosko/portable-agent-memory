# Required common profile review

Use this before producing a portable package and whenever an included source or its content changes. The common review compares the combined context across sources. A source's own profile review, a valid record hash or a ready-message cannot replace it. This applies to one selected source too; do not create a second fictitious source to satisfy the workflow.

## One coordinator, several source captures

Choose one main agent from the actual conversation and preserve that role. For example, the current work Codex can coordinate materials from its working context, the user's personal ChatGPT account and a selected Claude Code project. Source identities and scopes come from evidence; interface names alone do not establish distinct datasets. Do not assume a Claude account archive includes all Code project files or local instructions.

The user can provide raw archives, readable text or original files directly to the coordinator. A source-side export skill is optional. Treat prepared source records as a **capture**, not a ready combined bundle. Preserve source provenance, scopes, accessible evidence and missing coverage. Source-side confirmations must reflect real user decisions; a newly extracted file cannot declare itself the trusted previous profile.

Use one local common store outside synchronized folders. Its named coordinator and revision checks serialize changes; they do not authenticate a person or synchronize independent SaaS copies. Source agents can prepare materials while the coordinator continues available work, but must not overwrite the common review in parallel. Do not invent an automatic transfer of coordinator authority.

## Compare meanings before asking

Inspect the full combined input and any genuine prior confirmations. Use [profile-review.md](profile-review.md) for the evidence assessment and separate source-support check. Then classify every nonexcluded record in a common semantic review:

| Relation | Meaning and user-facing behavior |
| --- | --- |
| `equivalent` | Same meaning, exact kind and scope. Choose a real member as canonical; show it once with its aliases and sources. Preserve original records. At least two members. |
| `conflict` | Incompatible alternatives for the same intended fact/rule, exact kind and scope. At least two members; no automatic winner. |
| `compatible` | Independent or simultaneously valid context. One or more members; no aliasing or merging. Use single-member groups where appropriate. |

Different wording or IDs do not establish different facts. Conversely, a shared word or title does not establish equivalence. “Use short answers” and “Be concise” may match in the same scope; a detailed report rule limited to a particular project must retain that scope. Several mailboxes can coexist, while competing claims about one current primary mailbox may conflict. An archive's later download date does not prove that its contents supersede earlier statements.

Review groups against actual source evidence, including conditions, negation, history and ownership. The second semantic checker reviews the common conclusions, not only individual quotes. Use a separate checker when available; otherwise accurately label a second pass by the same model. Neither Python nor a fresh hash proves semantic truth.

## Exact semantic documents

Generate the semantic template from the common store. It includes current input and coverage IDs, but starts with `cross_source_checked: false` and no groups. Complete it after reading the actual combined input. Do not invent hashes or remove inconvenient records from coverage.

```json
{
  "format": "portable-semantic-review",
  "schema_version": 1,
  "input_sha256": "generated by common-template",
  "reviewer": {"kind": "same_model_second_pass", "label": "Actual reviewer and method"},
  "covered_record_ids": ["work-rule", "personal-rule", "project-rule"],
  "covered_source_ids": ["work-codex", "personal-chatgpt", "code-project"],
  "cross_source_checked": true,
  "groups": [
    {"id": "concise-replies", "relation": "equivalent", "record_ids": ["work-rule", "personal-rule"], "canonical_id": "work-rule", "note": "Actual source comparison supports the same meaning and scope."},
    {"id": "project-format", "relation": "compatible", "record_ids": ["project-rule"], "canonical_id": null, "note": "This rule applies only to its named project."}
  ]
}
```

This is a structural example with fictional IDs, not a completed check. Every nonexcluded record must appear in exactly one group. The covered sources must include the whole current source inventory, including unavailable or pending sources whose limitation was considered. For `equivalent` and `conflict`, record kinds and scopes must match exactly. `canonical_id` is a member only for `equivalent`; otherwise it is null.

Generate the second-pass template **after completing the review**. It starts uncertain. The checker produces:

```json
{
  "format": "portable-semantic-quality",
  "schema_version": 1,
  "review_sha256": "generated by common-quality-template",
  "reviewer": {"kind": "separate_agent", "label": "Actual checker; use same_model_second_pass if applicable"},
  "decision": "supported",
  "note": "Actual comparison of coverage, relations, scopes and sources; describe limitations."
}
```

Reviewer kinds are `same_model_second_pass`, `separate_agent`, `human`; use the real method and a real label. Decisions are `supported`, `uncertain`, `contradicted`. A template does not justify `supported`. Any edit to the semantic review requires a fresh quality template and real second pass. Named reviewer fields are caller attestations, not identity authentication.

## Preserve confirmed meaning; review the delta

A source addition or change invalidates the previous common check, even if no new records have arrived yet. When a migration inventory is linked, synchronize its changes before continuing. Inspect existing decisions and deferrals; work on new/changed records and the old semantic groups they affect. The new common review still covers the entire current inventory so cross-source conflicts are not missed.

Unchanged genuine user confirmations carry over. A newly found equivalent record may inherit the canonical member's confirmed decision only after the common semantic review and second pass establish equivalence. That is not permission to overwrite a different decision, broaden a scope or approve a changed meaning. Do not ask the same profile questions merely because another source repeats the same facts.

Resolve missing evidence from accessible material before asking the user to repair a technical omission. Ask one focused question only where the user's decision is needed. Show the relevant full content. Record `question_shown` only after actually presenting it; preserve `awaiting_answer` and user deferrals instead of repeating the prompt. A free-form answer can settle multiple shown records. Never mark an unseen choice approved.

Use the common store's event path for user decisions. Profile event schemas are in [profile-review.md](profile-review.md); outer command actor is the coordinator, while the event's `actor: user` means an actual user choice was recorded. Do not edit store internals, fabricate old confirmations or copy fresh hashes onto stale decisions.

## Commands from one authoritative store

Run from the installed skill folder with Python 3.10+. File paths refer to the actual execution environment. `COORDINATOR` is the chosen stable agent identifier; use the current revision from `common-view`, not a guessed number.

A provided source card is:

```json
{"id":"personal-chatgpt","label":"Personal ChatGPT — provided material","status":"provided","note":"Actual user-provided export; describe its coverage and missing items."}
```

Use actual source facts, not this fictional card. Statuses are `provided`, `pending`, `unavailable`, `excluded`; an excluded source card additionally requires `"excluded_by_user": true`, reflecting an actual user choice. A provided capture is a portable-memory JSON file prepared from accessible material; supply it even if it contains zero records. Omit `--memory` for other source statuses. Keep readable evidence separately for the assessment. Raw conversation archives must first be read/extracted; passing a ZIP filename as `--memory` is not extraction.

Reusing a source ID updates that source's capture. Omitted old records are retained, not silently deleted. Different sources must use distinct record IDs for differing content so one cannot overwrite another's claim. Source inventory choices and record-level historical/excluded decisions are separate; inspect existing records when changing a source's selection.

```text
python scripts/memory_tool.py common-create --store common.sqlite --coordinator COORDINATOR
python scripts/memory_tool.py common-source --store common.sqlite --source source.json --memory source-capture.json --revision CURRENT_REVISION --actor COORDINATOR
python scripts/memory_tool.py common-input --store common.sqlite --out combined-input.json
python scripts/memory_tool.py common-template --store common.sqlite --out semantic-review.json
python scripts/memory_tool.py common-quality-template semantic-review.json --out semantic-quality.json
python scripts/memory_tool.py common-review --store common.sqlite --assessment assessment.json --quality quality.json --semantic semantic-review.json --semantic-quality semantic-quality.json --revision CURRENT_REVISION --actor COORDINATOR
python scripts/memory_tool.py common-view --store common.sqlite
python scripts/memory_tool.py common-event --store common.sqlite --event profile-event.json --revision CURRENT_REVISION --actor COORDINATOR
python scripts/memory_tool.py common-result --store common.sqlite --out common-memory.json --report common-report.json
python scripts/memory_tool.py export common-memory.json --common-store common.sqlite --out memory-package.zip --assets selected-assets
python scripts/memory_tool.py inspect memory-package.zip
```

This is an outline, not a blind script. `common-input` returns `memory`, `sources`, `coordinator`, `revision`, `previous_profile_session` and an instruction. Read that complete input; save its `memory` value as a working JSON file when running `profile-quality-template --memory combined-memory.json --assessment assessment.json --out quality.json`. Construct actual assessment evidence using [profile-review.md](profile-review.md), perform the source-support check, and prepare the common semantic review plus its real second pass before calling `common-review`. Do not edit the common input or state to manufacture approvals. Omit `--assets` if no selected files are included.

`common-view` exposes the current revision, sources, `status`, `export_allowed`, `next_action` and `question`. Once the common check is valid, it also exposes `semantic_aliases`, `semantic_conflicts` and the nested `profile` view with records, agent tasks, questions and deferrals. Inspect both semantic conflicts and profile questions: a conflict detected by meaning is not necessarily the same group as a formal subject/predicate conflict. Ask the relevant focused question once. Statuses include `needs_common_review`, `needs_resolution`, `source_map_changed`, `partial` and `complete_within_supplied_sources`; the last explicitly means supplied sources, not a full account scan.

Record user choices with `common-event`. Explicit record exclusion changes semantic coverage, so regenerate the common review and its second pass for the remaining set before exporting. Already recorded user choices remain; rechecking membership is model work, not a reason to repeat them.

For an already confirmed profile, `common-create` accepts `--previous actually-confirmed-memory.json`. Pass only the genuine previous profile, not a newly extracted source dressed as prior approval. For an explicitly agreed partial scope, creation accepts `--allow-partial --scope-note "Actual agreed limitation"`; do not infer this choice from a delayed response.

If an existing migration inventory is part of this run, supply `--migration-store migration.sqlite` during creation. Run `common-sync --store common.sqlite --revision CURRENT_REVISION --actor COORDINATOR` after first linking it and after its sources/jobs change, then inspect and renew the combined review. Source synchronization does not download content. Run `common-source` again with changed material when it is available; neither a source-ready status nor an old quality file restores readiness by itself.

## Readiness and result boundaries

Normal completion and an explicitly agreed partial package are different outcomes. Partial mode needs an actual scope decision and meaningful note. It may retain unavailable/pending sources and deferred/unconfirmed records, but still requires the global semantic check and second pass. Unresolved conflicting active variants must remain pending in the exported projection, never active instructions. A partial result must identify its gaps; do not call it a complete account export.

The common result is a portable file and report containing `review` and `profile`. Choose new output/report paths when repeating the command. Export requires the current common store and checks that the result corresponds to its reviewed state. Individual `review`, `confirm` and `profile-result` commands remain preparation tools, not an export bypass. After binding project instructions into a skill or otherwise changing record meaning, register the changed capture and rerun the common check; ask again only for the changed content that needs a user decision.

Keep the source evidence and category coverage with the selected handoff materials. Excluding a record does not redact its text from an original archive if that archive is separately included. No common-profile operation reads SaaS accounts, installs a skill, writes native memory, restores automations or authorizes a connection.

At the receiver, the incoming review may not cover the actual union with existing memory. Import can stage files and preserve genuine user decisions while marking `common_review_required`; that is not permission to use the union as active instructions. Review this new combined input through the coordinator and issue a fresh common package. A receipt/content mismatch is detected by code; the new semantic conclusions still come from the host model or human. Never remove the marker manually.
