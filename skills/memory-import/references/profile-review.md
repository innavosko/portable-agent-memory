# Evidence, semantic checking and incremental profile review

Use this flow for the profile and rules that will guide the receiving agent. It separates source coverage, what the source actually supports, and the user's decision about current use. None of these checks alone proves the other two.

For the mandatory combined check before export, read [common-profile.md](common-profile.md). This reference supplies its evidence/quality schemas and review-event meanings. The standalone `profile-*` commands below can prepare a source or investigate a profile, but their output alone cannot pass the common export gate. When using a common store, record user decisions through `common-event` so the coordinator retains one review authority.

## Prepare evidence before asking the user

Read accessible source material and construct pending records using [records.md](records.md). Preserve conditions, exceptions, scope, ownership of accounts and provenance. Review all relevant categories without inventing absent values: `identity`, `goals`, `mailboxes`, `integrations`, `calendar`, `communication`, `documents`, `behavior`, `projects`, `workflows`, `resources`, `automations`.

Create an assessment with this exact structure:

```json
{
  "format": "portable-profile-assessment",
  "schema_version": 1,
  "sources": [{"id": "source-id", "locator": "actual source location", "text": "actual readable source text"}],
  "claims": [{"record_id": "record-id", "category": "communication", "subject": "user", "predicate": "preferred_language", "cardinality": "single", "evidence": [{"source_id": "source-id", "quote": "literal source excerpt"}]}],
  "coverage": [{"category": "communication", "status": "checked", "source_ids": ["source-id"], "note": "Actual scope of this check"}]
}
```

This is a shape example, not valid evidence. Real `quote` values must be nonempty exact substrings of the corresponding `sources[].text`; that source ID must also be declared in the record's `sources`. Read the real source before copying its text. A program can detect a mismatched excerpt, but cannot prove that pasted source text was honestly obtained.

Coverage statuses are `checked`, `unavailable`, `excluded`, `not_applicable`. State the real reason and source coverage. A missing category remains not checked; do not turn it into “none”, “not applicable” or a completed check. “Nothing found in these sources” is narrower than “the user has no such accounts or preferences”.

Use stable semantic `subject` and `predicate` values across equivalent facts, independent of their titles. Conflicts are grouped by category, normalized subject/predicate and record scope. Use `multiple` for simultaneously valid lists such as several mailboxes or roles; use `single` where values are alternatives. Do not choose `multiple` just to hide a genuine conflict. Different project scopes can legitimately have different rules.

The self-contained [profile-memory.example.json](profile-memory.example.json) and [profile-assessment.example.json](profile-assessment.example.json) are entirely fictional. They illustrate two valid mailboxes and one language preference; they are never a starting profile of the real user.

## Perform a separate semantic verification pass

Generate a quality template with the bundled command. Its initial verdicts are `uncertain`, not approval. A checker must compare each actual record and semantic annotation with the cited source, including conditions, scope, exceptions, dates and whether the address belongs to the user. A literal quote can still be irrelevant, negated or narrower than the proposed rule.

Use a separate agent/checker when available. If the same model performs a second pass, label that accurately; do not call it independent. The quality document is:

```json
{
  "format": "portable-profile-quality",
  "schema_version": 1,
  "reviewer": {"kind": "same_model_second_pass", "label": "Actual checker and review method"},
  "checks": [{"record_id": "record-id", "claim_sha256": "generated by the template command", "decision": "uncertain", "note": "What the source supports or leaves unresolved"}]
}
```

Reviewer kinds are `same_model_second_pass`, `separate_agent`, `human`. Replace the template's label with the actual checker. Verdicts are `supported`, `uncertain`, `contradicted`. Do not set `supported` merely because a quote/hash is valid, or give yourself a “100% quality” rating. If a checker lacks the source, retain uncertainty.

`claim_sha256` binds the record, its semantic annotation and referenced source text. Generate it through the command; do not copy an old hash after editing content. It is distinct from `content_sha256`, which binds the content shown for a user's review. Fresh technical QA can coexist with an unresolved conflict: quality-ready is not automatically confirmable. Valid unchanged user confirmations supplied as actual previous memory do not need a new model pass merely to ask the same questions again; a fresh contradictory check still needs attention.

## Keep one review state and ask only what matters

Create a profile session from memory, assessment and quality. `--memory` is a new extraction and starts pending, even if that file claims to contain valid active reviews. To reuse earlier user confirmations, separately pass the actual previously confirmed memory as `--previous`; never invent that file from the new extraction. Unchanged valid confirmations can then carry over. Use `profile-refresh` when continuing an existing session; its own unchanged decisions are retained. Inspect the view before asking anything. Its fields include `records`, `categories`, `conflicts`, `agent_tasks`, `question`, `awaiting_answer`, `deferred_questions`, `export_blocked_records` and `limitations`.

Resolve `agent_tasks` from accessible sources rather than asking the user to fix missing technical evidence. Ask one focused question when the user's choice is needed: a contradiction, a changed fact or uncertain current use. Show the relevant full content and meaningful options. Use known answers and unchanged valid confirmations; do not repeat the entire profile interview. A free-form reply may settle several visible records, but never fill decisions for unseen content.

After actually presenting a question, record `question_shown`. `awaiting_answer` means wait without repeating it. A user can defer a question with a reason; save that choice and continue independent work. `reopen` brings back a deferred question when requested or when the user explicitly returns to it. Unchanged issues keep their review/deferral state; changed issue content needs a fresh check.

Public events use `{id, actor, type, data}`. `actor` is `user` or `agent`; attributing a record to `user` must reflect an actual user decision, not an automatic agent approval.

| Type | Data | Use |
| --- | --- | --- |
| `review` | `decisions: [{id, content_sha256, decision}]` | Actual shown-content decisions: `active`, `historical`, `exclude`, `pending` |
| `question_shown` | `question_id` | Question really presented, never marked in advance |
| `defer` | `question_id`, `reason` | Preserve the user's choice to return later |
| `reopen` | `question_id` | Revisit a deferred issue |
| `coverage` | `category`, `status`, `source_ids`, `note` | Record a real check or access limitation |

Corrected facts require new records/evidence/quality via `profile-refresh`, not just an answer string that silently rewrites memory. Refresh retains older records omitted from the new input: omission is not deletion. Use explicit review choices for exclusion or historical retention. Refresh invalidates outdated QA/confirmation when meaning, scope or evidence changes. Do not edit state internals or bypass a stale revision error.

## Commands and result

Run from the installed skill directory with the available Python 3.10+ interpreter. Files must be in its actual execution environment. For a demonstration, copy the fictional examples to an isolated working folder; for real work build actual data and assessment.

```text
python scripts/memory_tool.py profile-quality-template --memory memory.json --assessment assessment.json --out quality.json
python scripts/memory_tool.py profile-create --memory memory.json --assessment assessment.json --quality quality.json --out profile-state.json
python scripts/memory_tool.py profile-create --memory new-extraction.json --assessment assessment.json --quality quality.json --previous actually-confirmed-memory.json --out resumed-profile-state.json
python scripts/memory_tool.py profile-view profile-state.json --format json
python scripts/memory_tool.py profile-event profile-state.json --event profile-event.json --revision CURRENT_REVISION --out profile-state-next.json
python scripts/memory_tool.py profile-refresh profile-state-next.json --memory updated-memory.json --assessment updated-assessment.json --quality updated-quality.json --revision CURRENT_REVISION --out profile-state-refreshed.json
python scripts/memory_tool.py profile-result profile-state-refreshed.json --out reviewed-memory.json --report profile-report.json
```

Generate the template, perform the semantic check, then create/refresh state with the completed quality file. The two create commands show alternatives: a new review, or new extraction compared with genuinely existing confirmations. Do not run the entire sequence blindly. Each output state becomes the one authoritative input for the next operation; preserve the latest state during handoff. These JSON files do not automatically coordinate separate SaaS copies.

`profile-result` produces an intermediate safe portable memory copy and report; unresolved active facts with blocked evidence/conflicts are demoted to pending. It does not save native memory or configure the receiving service. Register the prepared material with the common coordinator, complete [common-profile.md](common-profile.md), and export its current result with the common store. Retain coverage, pending questions and actual checker identity with the handoff.
